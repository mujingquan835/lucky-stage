# 架构与维护约定

- `server/domain.ts`：活动聚合与抽奖规则，不依赖 HTTP。
- `server/db.ts`：统一 SQL/transaction 接口，生产 pg、本地 PGlite。
- `server/app.ts`：登录保护、同源请求、输入与上传、业务接口。
- `server/security.ts`：密码验证、会话 token 摘要。
- `server/workbooks.ts`：Excel 模板、读入与导出，限制压缩文件大小和解压大小。
- `server/snapshot.ts`：含图片的校验备份和空库恢复。
- `web/src/App.tsx`：管理界面与操作流程；`Stage.tsx`：独立展示接口与轮播；`api.ts`：网络封装。

## 数据结构

PostgreSQL `activities(id TEXT PRIMARY KEY, data JSONB NOT NULL)`，每场活动作为一个聚合保存配置、参与者、礼品、抽奖轮次和操作日志。`sessions` 保存 token SHA-256 与过期时间，不保存原始 token。

首版采用 JSONB 活动聚合来简化库存、参与资格、幂等结果及日志的一致保存。每次修改 `SELECT ... FOR UPDATE` 锁住本场活动行；不同活动互不阻塞。PGlite 在进程内排队执行事务，使用相同 SQL。活动内电话唯一和库存约束由同一锁下的域逻辑维护，不允许绕过域函数直接修改活动。

单场上限 10,000 人、单轮最多 50 人。当前每次读取和更新整个活动聚合，长时间高频抽奖或巨量历史会增大 JSONB 文档；适合人工操作的活动场景。若后续需要持续并发、大量轮次或统计检索，再迁移到独立人员、礼品、轮次和中奖记录表，保留服务接口与行为测试。

## 抽奖事务

同一事务：锁活动 → 查请求 ID 和参数摘要 → 校验归档、库存、参与资格 → 安全随机抽样 → 写中奖快照、原始回执和日志 → 提交。

请求 ID 相同、参数相同返回原回执；参数不同返回 409。作废修改历史展示状态，但原回执保留。查询回执用于故障恢复，当前有效状态以中奖记录为准。随机结果先持久化，再播放动画；关闭网页不会撤销中奖。

图片使用随机 UUID 文件名，sharp 解码并重新编码 WebP，大小上限 5 MB、输入像素上限 4000 万。图片目录不直接公开，只通过登录保护的接口读取。当前不自动删除无引用图片，避免误删历史记录或并发备份所需图片；可在后续维护工具中实现带引用检查的清理。

## 权限与限制

一个管理员角色，无公众登录和注册。密码由环境变量提供，启动时用随机 salt scrypt 产生验证摘要；会话原 token 仅存在 HttpOnly Cookie，数据库保存摘要。Cookie 有效 12 小时，生产启用 Secure。修改请求同时验证 Origin 和自定义请求头。

大屏仅读取去掉电话和不展示字段的 `/stage` 接口。手机可管理，现场建议电脑投屏。首版无第三方随机公证、扫码签到、短信、公众报名、分组筛选、内定中奖和付费功能。

## 后续维护

规则变化先修改设计和行为测试；常规验证为测试、类型检查、构建和浏览器演练。代码格式化使用 `npm run format`。任何部署、域名变更或购买服务均由用户确认后执行。真实数据不入 Git，测试使用虚构数据。
