# 活动抽奖系统设计稿

日期：2026-10-27  
状态：用户已确认进入开发；本地实现与验收情况见 docs/maintenance/acceptance.md

## 1. 目标与确认范围

建设可以长期复用的 Web 活动抽奖系统，后台提前维护参与名单和礼品，现场使用浏览器大屏展示抽奖。

用户已确认：
- 使用联网后台版。
- 名单字段包含姓名、公司、电话、门店名称。
- 礼品字段包含名称、数量、图片。
- 单人抽奖：选中名单中的某个人，由此人随机抽取一份礼品。
- 支持批量抽奖。

以下为设计建议，随本稿一起确认，不视为用户已逐项同意。

## 2. 方案选择

考虑过本地单机版和联网后台版。单机版部署简单、可离线，但数据迁移和多设备管理不便；联网版集中保存数据，适合重复举办活动，但需要服务器、数据库和登录保护。用户选择联网后台版。

第一版采用一个组织、一个管理员角色，可创建多场彼此隔离的活动；不建设公众注册、扫码参与、短信登录、多租户计费、指定中奖或付费抽奖功能。普通参与者无需登录或使用手机。

## 3. 页面与视觉

### 管理后台
- 活动列表：创建、复制配置、归档活动；复制不包含名单和中奖记录。
- 活动概览：参与人数、剩余可抽人数、礼品剩余份数、中奖记录数，进入大屏入口。
- 名单管理：手工增改、Excel 模板下载与导入、搜索、导出；支持姓名、公司、门店、电话查询。
- 礼品管理：名称、图片、总数量、剩余数量、显示顺序、是否参与单人抽奖。
- 抽奖控制台：切换模式、选人或选奖品、设置批量人数、开始抽奖和查看结果。
- 中奖记录：按人、礼品、时间搜索，导出明细；作废操作填写原因并保留历史。
- 活动设置：活动名称、背景图、主色、重复中奖开关；重置和归档等重要操作需二次确认。

### 现场大屏
默认采用喜庆红色和暖金色，后台采用清爽浅色。活动可更换背景、活动名称、品牌图片和主色。

大屏以 16:9 投屏为优先：上方活动名称，中部礼品图片和抽奖动画，下方本轮中奖结果；控制项收进管理员操作面板。单人模式突出参与者姓名、门店和抽中礼品；批量模式突出本轮礼品并网格展示中奖人，人数较多时分页。批量每轮上限暂定 50 人，默认 1 人。

后台支持桌面和手机管理，大屏支持全屏。没有匿名公开名单页。投屏展示需先登录，电话不展示，公司和门店可在活动设置中关闭。管理入口隐藏不代表权限隔离，所有 API 均需验证管理员权限。

## 4. 名单与礼品

姓名、电话必填，公司和门店名称可空；电话按文本保存，保留前导零和国家区号。导入先预览并展示错误，不静默丢弃行。去除电话首尾空格后，以活动内电话完全一致判断重复；用户修正后统一确认导入，整次导入成功或失败。第一版仅接收 .xlsx，建议单场不超过 10,000 人。

中奖后保留当时姓名、公司、门店和礼品的快照，后续资料修改不改变历史记录。已有有效中奖记录的参与者不可删除，可停用；已抽出的礼品不可删除，可停用。

图片支持 JPEG、PNG、WebP，单张最多 5 MB，服务端验证实际文件类型并生成存储文件名；不执行上传内容。图片必须上传到持久存储，不能仅依赖客户端临时地址。

礼品数量为正整数，剩余库存由总数量减有效中奖份数计算；总数量不能调低到已发放数量以下。

## 5. 抽奖规则

默认同一活动每人最多中一次，两种模式共享中奖状态。可在活动开始前开启允许重复中奖；首轮抽奖后锁定此规则，避免中途更改口径。即使允许重复，同一批次内每人最多出现一次。

### 单人模式
1. 管理员搜索并选择一位启用且符合中奖规则的参与者。
2. 系统展示参与者信息及可抽礼品范围，管理员点击开始。
3. 服务端按参与单人抽奖的礼品剩余份数加权随机选择一份；例如剩余 10 份和 2 份，概率为 10:2。
4. 原子保存中奖结果并扣减库存，再返回前端播放动画和揭晓结果。
5. 参与单人模式的礼品没有库存时禁止开始，提示补充或调整礼品。

### 批量模式（建议）
1. 管理员选择一个礼品和本轮中奖人数。
2. 从本活动所有启用且符合规则的人中等概率、无放回随机抽取；第一版不做公司或门店分组筛选。
3. 中奖人数必须同时小于等于剩余礼品数量、合格人数和 50 人上限，否则拒绝并展示可用数量，不自动缩小抽取规模。
4. 一次事务保存整批结果，再由前端揭晓。同一轮每人获得所选礼品一份。

本轮开始后禁用重复点击与模式切换。随机选择由服务端使用适合随机抽样的安全随机源完成，无内定和概率暗调功能；这是可留记录的业务随机抽奖，不宣称具备第三方公证能力。

## 6. 数据一致性与故障处理

所有抽奖请求具有活动内唯一请求标识，同一请求重试返回相同结果。服务端在数据库事务中按活动串行处理抽奖、相关库存修改和记录作废，并重新检查参与资格和库存；多设备同时操作不得超发，也不得违反重复中奖规则。

网络超时先查询原请求结果，不直接发起新的抽奖。刷新、退出全屏或动画中断不会重抽；可从最近一轮继续展示。未收到服务端确认时显示“结果确认中”，不展示虚构的成功结果。断网时暂停新抽奖，联网后恢复查询。

作废保留原记录、原因、操作者和时间，释放对应礼品库存；默认禁止重复中奖时，参与者在没有其他有效中奖记录的情况下恢复资格。作废不自动补抽；管理员明确发起下一轮。每个中奖结果最多作废一次。

活动归档后只读；“重置”通过复制出新活动开展下一次抽奖，原记录保留，不清空历史。抽奖、作废和关键配置变更写入操作日志。

## 7. 技术与部署建议（由设计方提出）

采用 React + TypeScript 前端、Node.js + TypeScript 服务端、PostgreSQL 数据库，使用数据库事务保证抽奖一致性。采用单个应用部署，暂不拆微服务。

提供 Docker Compose 部署方式，可部署至支持 Docker 和 HTTPS 的云服务器。礼品和背景图片使用持久文件卷，数据库使用持久卷；部署文档覆盖数据库与图片的联合备份、恢复和升级。正式上线前需用户提供服务器或选择托管地点、域名；这些不阻碍本地开发和验证。服务器购买、付费服务开通和正式发布需用户另行授权。

管理员账号不开放注册，部署时通过环境配置初始化，密码存储哈希；使用安全会话 Cookie，服务端校验权限和修改请求来源，登录有频率限制。完整电话仅在已登录后台查看和导出，不写入普通应用日志。

不在源代码提交真实名单、密码或生产配置。示例数据使用虚构信息。开发交付建立 README、AGENTS.md、环境变量示例、维护说明和 Git 版本管理。

## 8. 第一版交付与验收

交付完整项目源码、可运行本地版本、部署配置、Excel 名单模板、后台与大屏、操作及维护说明。没有服务器前明确标记为本地已验收、线上待部署，不把本地运行当作已上线。

验收重点：
- Excel 可预览导入，错误和重复电话有明确提示。
- 名单、图片、库存与记录刷新后保留。
- 选定参与者随机抽礼品，批量按指定礼品抽出指定人数。
- 两种模式共享库存和中奖资格；库存耗尽、人数不足均不能抽奖。
- 并发和重复请求不超发、不重复落库；超时重试能找回原结果。
- 作废记录可追溯且库存正确恢复，归档活动不可修改。
- 未登录无法访问名单、抽奖、导出及管理接口。
- 大屏可投屏，无电话泄露，批量结果不溢出页面。
- 提供备份恢复操作，并用虚构数据验证恢复。
